# ChatGPT GitHub 作業指針

このリポジトリをChatGPTから変更する際は、以下を原則とする。

## 1. 常に最新状態を基準にする
- 作業開始時に `main` の最新HEADを取得する。
- 対象ファイルは必ず最新の `main` から取得する。
- 対象ファイルの現在のblob SHAを取得し、そのSHAを更新操作に使用する。
- 過去のチャット、過去に取得したSHA、過去のファイル内容を現在の状態として扱わない。

## 2. 変更は一度に一つずつ行う
- 複数ファイルを同時に更新しない。
- 1ファイルの更新が成功したことを確認してから、次のファイルへ進む。
- 更新後は返されたコミットSHAと対象ファイルの状態を確認する。
- 次の変更では、直前の成功したコミットを基準に最新状態を再取得する。

## 3. 既存ファイルを丸ごと再構成しない
- 単純な変更の場合、元ファイルの構造・内容を可能な限り保持する。
- 必要な箇所だけを変更する。
- 特にminified CSSや大きなデータファイルについて、ChatGPTが内容を記憶から再構成して全文置換することを避ける。
- ファイル全体を更新する必要がある場合も、必ず直前に取得した最新内容を唯一の基準とする。

## 4. 成功した操作経路を優先する
- 同じ種類の変更で過去に成功した操作手順がある場合、それを優先して再現する。
- 不必要にBlob/Tree/Refなど別の低レベルGit操作へ切り替えない。
- `update_file` など、実際に成功実績のある経路をまず使用する。

## 5. ブロック・失敗時に闇雲に再試行しない
- 同じ操作をそのまま繰り返す前に、最新HEAD、対象ファイルSHA、対象ファイル内容を再取得する。
- 「安全確認ブロック」をGitHub側の障害と決めつけない。
- 操作内容、対象ファイル、SHA、コミット順序などの手順上の差異を確認する。
- 変更が実際にコミットされていない限り、「実装完了」と報告しない。

## 6. Workflowまで確認する
サイト変更では、ファイル更新だけで完了としない。
1. コミット生成を確認
2. `main` に反映されたことを確認
3. GitHub Actions / Pages Workflowが起動したことを確認
4. Workflowの成功を確認
まで行う。

## 7. 作業結果を正確に報告する
- 成功したファイルと未成功のファイルを明確に分ける。
- コミットされていない変更を「変更済み」と表現しない。
- GitHub側のエラーとChatGPT側のツールブロックを区別する。
- 原因を断定できない場合は推測として明示する。

## 8. 今回の教訓
- 「最新SHAを取得したから安全」とは限らない。取得後の内容と更新操作まで一貫して最新状態を維持する。
- 同じ操作が失敗した場合でも、単純な権限障害と決めつけず、操作手順そのものを比較する。
- Worksで成功した手順がある場合、CharactersやSongsにも同じ手順を順番に適用する。
